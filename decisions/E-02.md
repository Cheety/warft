# E-02 — Runtime and language

**Status:** ruled · **Source:** panel E-02 of the architecture overview, revision 2 (`workpod-plattform-leitstand.html`), carried over per AP-0.1. Translated under [the language ruling](language.md); the identifiers are untouched.

## Ruling

One statically linked Go binary for the control plane, the scheduler, the worker, the adapters, both gates and the agent harness. Postgres as the only state database, with the queue inside it. containerd with runc; gVisor exclusively for pods at authority level `public`.

## Rationale

1. **One binary, no runtime on the host** — the demand from A-01, verbatim. Node or Python would need an interpreter in the image and would contradict it in the first sentence.
2. **Go instead of Rust:** the surface is large (adapters, scheduler, two gates, harness), the work is I/O- and database-bound, and containerd, OCI, gRPC, Postgres and nftables are first-class there. Rust would win where foreign formats are parsed — the gates check rules, they parse nothing.
3. **The agent harness is the same binary,** mounted read-only into every pod. That way no container image has to bring the agent along, and a harness update is an image update instead of a rebuild of all container images from T-03.
4. **The queue in Postgres with `SKIP LOCKED`, no second broker.** At the rates of one cell (V-03) a broker is an additional failure part with no return — and V-02 demands leases anyway, not delivery.
5. **gVisor bound to the authority level, not to a setting.** The expensive isolation then applies automatically exactly where T-01 classifies the text as untrusted, and nowhere else.
6. **4 cores and 16 GB for the control layer** (V-01) are realistic rather than optimistic with Go and Postgres. That is the number the whole economics of V-01 hangs on.

## Overturned by

a gate that has to parse a non-trivial format — then Rust for that one gate. Or measured write rates above roughly 5,000 per second in one cell — then a broker, and only then.
