# E-05 — Class mix and constants

**Status:** ruled · **Calibrated:** 2026-07-26, AP-1.3, [run 30204671464](https://github.com/Cheety/warft/actions/runs/30204671464) · **Source:** panel
E-05 of the architecture overview, revision 2 (`workpod-plattform-leitstand.html`), carried over per
AP-0.1. Translated under [the language ruling](language.md); the identifiers are untouched.

## Ruling

The five constants are planning values of the occupancy table, not operating values. Admission and
preemption decide exclusively on PSI and measured peak RSS (R-C). The mix behind the given values is
20/30/35/15 across tiny/small/medium/large.

That is the rule, and the calibration run of AP-1.3 did not touch it. What the run changed is the
numbers, which is what its own overturn condition asked for:

| Constant | Given | Measured | R-D computes with | The measurement |
|---|---|---|---|---|
| host and runtime, `control` | 12288 MB | 334 MB | measured | a floor: no control plane in the image yet (AP-3.1) |
| host and runtime, `work` | 6144 MB | 328 MB | measured | `MemTotal - MemAvailable` at rest, 4 cores · 5905 MB |
| page cache baseline | 8192 MB | 60 MB | measured | a floor: no base layers to share yet (AP-3.3) |
| pages per frozen pod | 24 MB | 0.37 MB | measured | marginal cost over 240 frozen pods carrying nothing but themselves; 1.38 MB when a pod holds a megabyte of state |
| zram factor | 1.6 | 4.41 | measured | 415.1 MB of frozen pages into 94.2 MB of memory · pure ratio 4.56 · 0 same-filled pages |
| active pod, cores | 0.8 | 0.190 | **given, until AP-3.7** | the mix at 1/8 of each class request, on 4 cores · 5905 MB |
| active pod, RAM | 960 MB | 122.5 MB | **given, until AP-3.7** | same window; per-class numbers in the run |

`acceptance/e05-constants.tsv` is the same table in the shape R-D reads it in, and
`acceptance/calibration.sh` holds the two against each other on every run: a number here that is not
there is drift, and a fresh measurement more than a factor of two away stops the run.

**The active pod is measured and not adopted.** The panel's own "measured in" column says where each
constant is measured: four say A-06, and the active pod says "three runs per repository (R-C)". At
stage 1 there is no repository and no job — no harness (T-01), no container image (T-03), no runtime
(AP-3.1) — so what a pod costs when it works cannot be measured, only what twenty shells cost while
they hash a file. That number is recorded above because it was measured; the table keeps 0.8 cores and
960 MB until AP-3.7 measures the real one, because a planning value taken from a load one eighth the
size of the class it stands for would plan slots that are not there.

## Rationale

1. **This bounds the risk of wrong constants completely:** the table plans imprecisely. It cannot
   overbook the machine, because the runtime does not read it. That is the real conclusion of this
   point — not the number, but the place where it takes effect.
2. **The mix adds up:** 0.2·0.1 + 0.3·0.3 + 0.35·1.0 + 0.15·2.0 = 0.76 cores and 0.2·128 + 0.3·384 +
   0.35·1024 + 0.15·3072 = 960 MB. The table's given values therefore describe a build-heavy
   operation — that had not been said anywhere so far and is the actual finding.
3. **A read- and plan-heavy mix (30/40/25/5)** yields 0.5 cores and 600 MB and thus about half as
   many slots again. On a platform whose everyday work is reading, planning and summarizing, the mix
   will move in that direction — the given value is deliberately the pessimistic one.
4. **Conservative is the right direction here.** Too few planned slots cost money. Too many cost the
   evidence from R-C, and that is more expensive.
5. **Every measured number moved in the direction "the table planned too pessimistically", and two of
   them are floors.** Host and runtime is 328 MB instead of 6 GB because the control plane,
   containerd's per-pod runtime and the gates are not in the image yet; the page cache is 60 MB
   instead of 8 GB because nothing shares a base layer yet; the zram factor is 4.41 instead of 1.6,
   which the panel itself predicted — its own note next to the given value reads "usually better in
   reality". Adopting them is right anyway: a planning value that describes the machine as it is
   beats one that describes a
   machine nobody has built, and the condition under which each floor rises is named above and dated
   to a work package. What would not be right is presenting a floor as final, which is why those rows
   say floor.
6. **The frozen pod is the number with the most consequence and the most room to move.** R-D divides
   it by the zram factor and multiplies it by the whole fleet, so it decides how large a fleet a node
   can carry at all. 0.37 MB is the mechanism alone — one cgroup, one shell, no harness — against
   24 MB for "harness plus runtime in the freezer". The harness is what closes that gap, and it
   arrives in AP-3.1.
7. **The zram factor is the one constant the run measured under the conditions it will actually
   work in:** the pages of pods that had been frozen, compressed by the algorithm the image selects,
   read off the device rather than assumed. 4.41 against a given 1.6.

## Overturned by

The calibration run from A-06 — **which has now happened**, in AP-1.3. It changed numbers and no
rules, and entered them into the table instead of discussing them. That condition is spent; three
narrower ones take its place:

- **the next calibration run**, after AP-3.1 puts a runtime and a harness in the image and AP-3.3 puts
  container images on a node. Host and runtime, the page cache baseline and the pages per frozen pod
  are floors until then, and the same script re-measures them.
- **R-C's three runs per repository (AP-3.7)** for the active pod, which is the one constant this run
  recorded without adopting.
- **the rule itself** would fall only if admission or preemption ever read this table. They read PSI
  and measured peak RSS (SP-RD-3); a change to that is a change to R-C, not to a number here.
