# Decision: where the image signing key lives, and what a signature covers

**Status:** ruled · **Date:** 2026-07-25 · **Affects:** SP-A03-1, SP-A03-3, SP-A03-7, AB-A03-7,
AP-0.2, AP-1.2.

AP-0.2 carries the task *"generate the signing key; do not place the private part on a build
machine"*, and `AB-A03-7` ("SBOM and signature — present and verified per image") cannot turn green
without answering where the private half goes instead. The specification states the constraint
(SP-A03-3: "the public key lies in the boot path, the private one not on the machine") and names no
mechanism. This file is the mechanism.

## Ruling

**One X.509 key pair, RSA-4096, generated once.** The same pair signs the image seal now and the
dm-verity roothash in AP-1.2 — there is not a second key for a second purpose.

The **private half** is generated by the repository owner with `image/genkey.sh`, passphrase-encrypted,
outside the working copy (`~/.config/warft/signing.key` by default, mode 0600). It is never a CI
secret, never on a platform node, never in Git. `genkey.sh` refuses to run when `CI` is set, so the
constraint is enforced by the script rather than remembered.

The **public half** is `image/signing.crt`, committed. In AP-1.2 that is the certificate that goes
into the boot path.

**What the signature covers** is a *seal record* — `image/seal/image.seal`, written by `build.sh`
after the two passes have been compared. It holds the sha256 of every artifact including the SBOM,
and above them the inputs that produced them: the revision of `image/`, `SOURCE_DATE_EPOCH`, the
package pin, and the pinned mkosi version. Signing that one small file therefore seals the image,
the SBOM and the build inputs together, in a file a person can read.

**Sealing happens where the key is; verification happens everywhere.** `image/seal.sh` needs the key
and signs the record. `image/verify.sh` needs only the committed certificate: it rebuilds the seal
record from the artifacts in front of it, compares it to the sealed one, checks the signature, and
checks the SBOM is present and parses. CI runs `verify.sh` on every push and never holds a key.

That split works **only because `AB-A03-2` holds**. A bit-identical rebuild makes the artifact hashes
a function of the inputs, so one signature made once covers every later rebuild of the same inputs.
The two rows hold each other up: if the build stops being reproducible, the seal stops verifying.

## Rationale

1. **The verity key is needed anyway, and it is this key.** SP-A03-3 requires a signature the boot
   path can check offline, against a certificate on the ESP. That is an X.509 pair and nothing else.
   Generating one now and using it for both means AP-1.2 inherits a key with a history instead of
   minting a second one.
2. **Keyless signing was considered and rejected.** Sigstore (`cosign` with the CI's OIDC identity)
   would satisfy "no private key on a build machine" by construction and would turn `AB-A03-7` green
   with no human step at all. It fails on two counts: it makes Fulcio and Rekor trust roots that the
   specification never names — the kind of thing V-05 says is a decision, and this one has no
   argument behind it — and it produces a bundle the kernel cannot check at boot, so AP-1.2 would
   need a real key regardless and the work would be done twice.
3. **The constraint is checkable, not aspirational.** No workflow reads a signing secret, `verify.sh`
   takes no key, and `genkey.sh` aborts under CI. "Not on a build machine" is a property of the
   repository that can be read off it.
4. **A passphrase, because the realistic threat is the workstation.** With one person there is no
   offline signing host and no hardware token; the key sits on the machine its owner uses daily.
   Encrypting it at rest is the difference between losing the machine and losing the root of trust.
5. **An unsealed revision is not a failed one.** During AP-1.1 the image changes on nearly every
   commit, and demanding a re-seal per commit would make the seal an obstacle to be routed around,
   which is how such mechanisms die. `verify.sh` distinguishes *unsealed* (exit 2, reported, does not
   fail the build) from *sealed and wrong* (exit 1, fails). The gate that an unsealed image reaches
   no channel is SP-A03-1's, and it belongs to AP-6.4 where the channels are built.

## Consequences

- `AB-A03-7` turns green only through a run in which `verify.sh` exited 0, and goes back to unsealed
  whenever the image inputs change without a re-seal. That is the intended behaviour, not drift.
- Re-sealing is deliberate work with the same shape as bumping the pin: build, compare, sign the
  record, commit it with the run named in the message.
- AP-1.2 points mkosi's `VerityKey=` and `VerityCertificate=` at this pair; `image/signing.crt` moves
  into the boot path there. No new key is generated at that point.
- The key pair does not exist until the owner runs `image/genkey.sh`. Nothing else in the repository
  can create it — that is the ruling working, not a gap in it.
- Filed under [the deferred two-person rule](two-person-rule.md): with one person in the project,
  this decision was ruled alone, as that file permits.

## Overturned by

A second person joining the project, the first delivery to anyone outside it, or the platform
building its own images (SP-A03-8) — whichever comes first. A key on a workstation is adequate while
the only consumer of the signature is its owner; it is not adequate the moment somebody else boots
what it signed, and it is plainly wrong once an automated builder needs to seal. At that point the
private half moves to a hardware token or a signing service the build calls without ever holding the
key, and this file is replaced rather than amended — `image/signing.crt` need not change, because
only the custody of the private half does.
