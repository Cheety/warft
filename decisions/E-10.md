# E-10 — Authority and interfaces

**Status:** ruled · **Source:** panel E-10 of the architecture overview, revision 2 (`workpod-plattform-leitstand.html`), carried over per AP-0.1. Translated under [the language ruling](language.md); the identifiers are untouched.

## Ruling

The authority from K-04 is a Biscuit token. All interfaces — control API, worker pull, gates, events — are Protobuf over gRPC, mTLS with the node certificates from B-01. The wire is Protobuf, the state stays relational (E-02): in Postgres there are columns, not serialized blobs.

## Rationale

1. **Why not JWT:** no offline attenuation. A captain that produces subjobs would have to call the control plane for every new authority — K-04 says it attenuates by itself, and that is exactly what a JWT cannot do.
2. **Why not Macaroons:** attenuation yes, but verification needs the originating secret — a shared standing secret in every gate, which B-01 has just forbidden.
3. **Caveats are data, not code.** `targets`, `budget` and `expires` from K-04 stand as facts in the token; evaluation at the gates is deterministic and bounded. A gate executes nothing, it verifies (B-02).
4. **One schema, several renderings.** Exports (V-05) and the audit trail (B-03) render from the same Protobuf definitions; there is no second, human-maintained format that could drift.
5. **The same contract inside the pod too.** Harness and worker speak the same schema over the local socket (T-04) — from the adapter through to the gate, exactly one interface schema in the system.

## Overturned by

For the token, nothing about the property — a standard offering offline attenuation with public verification would be a library change, not a reversal. for the wire: first-class third-party clients in the browser — then grpc-web as a second rendering of the same schema, never a second api.
