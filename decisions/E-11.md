# E-11 — Order

**Status:** ruled · **Source:** panel E-11 of the architecture overview, revision 2 (`workpod-plattform-leitstand.html`), carried over per AP-0.1. Translated under [the language ruling](language.md); the identifiers are untouched.

## Ruling

Build in this order, and every step ends with a measurement instead of an opinion. No step starts before the previous one has delivered its number.

| Step | Result | Measures |
|---|---|---|
| 1 | A-06 as a script — against a bare mkosi VM; the base holds, or E-01 falls | the five constants (E-05) |
| 2 | K-01, K-02, E-10 — schema, migrations, worker interface; the contract everything else is built against | nothing, that is the point |
| 3 | smallest system — `role = all`, one adapter (CLI), one pipeline, one runner, **without a captain**, jobs by hand | T-04, T-05, R-A, K-02, K-03 |
| 4 | handles from F-03 — the ten handles first; they need no model and are checkable before any agent question; `fact.query` reads the store from E-09 | success rate per handle |
| 5 | Q-01, then the captain — the intent contract before the model that uses it | share without a clarification |
| 6 | second node — `role = work`: intake, lease, expiry, rolling update | V-02, and only then V-03 |
| 7 | Q-04 — the regression corpus **before** the first model change | `escape_rate` |

## Rationale

1. **Step 3 without a captain is not a detour.** A system whose mechanics first run together with a model has two unknown sources of error and no way to separate them.
2. **Step 4 before step 5,** because handles need no model: they are the only layer that can be proven completely before anything is guessed.
3. **The jump to several cells is small afterwards** — the same software a second time, provided K-01 carries the cell identifier from the start. That is the only reason this one field is mentioned in two places in this document.

a red result in step 1. Then the base changes, not the order.
